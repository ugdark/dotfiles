# QA検証依頼コメント作成

issueに対するQA観点の依頼コメントを、形式を揃えて作成する。固有情報（PR・コード識別子・URL・環境名）はテンプレートの置き換え部分として、実行時にissue/PR/差分から取得する。**このスキル自身には固有情報を書かない。**

## 実行フロー

### Step 1: 材料の取得

`$ARGUMENTS` または会話からissueを特定し、`gh issue view` と関連PR（`gh pr view` / `gh pr diff`）から以下を読み取る。

- 修正PR
- 変更内容（ユーザーから見た挙動）
- 変更箇所と、その影響範囲（共通処理か、特定画面だけか）
- 異常系で、画面から再現できないもの
- 環境・前提（検証環境名など）

読み取れない項目のみ AskUserQuestion で聞く（質問は1つずつ）。

### Step 2: 本文を作成

```markdown
## QA検証で確認していただきたいこと

修正 PR: <PR参照>

<変更内容を1〜2文。ユーザーから見た挙動で書く>
変えたのは、<変更箇所>だけです。
<影響範囲が広い場合のみ> ただし、<理由>ので、リグレッションの確認をお願いします。

### リグレッションの観点（<環境>）
- <操作と期待結果。1行1観点>

### 修正した異常系
<画面から再現できない異常系と、その確認手段（単体テスト等）。なければこの節ごと省く>
```

### Step 3: ユーザー確認

投稿前に本文を表示して承認を得る。承認後、`gh issue comment` で投稿する。

## 書き方ルール

- **観点は操作→期待結果**で書く。実装用語ではなくQAが画面で確認できる言葉にする
- **変更していない挙動の確認**（権限エラー画面など）は「修正前と同じく」と明記する
- **画面から再現できない異常系**はQAに依頼せず、確認済みの手段を書くだけにする
- 観点は影響範囲から導く。変更箇所が共通処理なら、その処理を通る代表操作を挙げる
- 短く書く。差分から読み取れる実装詳細は書かない

## 重要ルール

- **投稿前確認は必須**: Step 3を省略しない
- **固有情報をスキルに書かない**: 例示を足す場合もダミー値にする。実在のリポジトリ名・PR番号・パス・識別子を入れない
- **個人設定ファイルへの参照を含めない**: コメント本文に個人ローカルのパスや識別子を含めない
